# 月影の村 — オンライン人狼

React + TypeScript + Vite の日本語Webアプリです。GitHub Pagesは静的フロントエンドを配信し、Firebase Authentication（匿名認証）と Callable Cloud Functions がルーム状態・役職・行動・勝敗を管理します。Realtime Databaseのルーム本体はクライアントから読めず、Cloud FunctionsだけがAdmin SDKで読み書きします。認証済みクライアントは参加中ルームの更新番号と、共有・人狼チャットの参加者向け更新番号だけを購読できます。参加者に返す画面情報は関数内で整形します。更新番号の読み取りもルーム参加者・観戦者・現在の管理者に限定します。

## 現在の実装範囲

- ルーム作成、5桁コード発行、参加、招待URL/QR、3〜20人の人数チェック
- 人数別おすすめ役職構成、議論時間、夜と役職確認の自動/手動進行、初日襲撃、同票処理、投票結果公開、オープンルール、初日白通知
- ポイント制（ルーム内累計、勝利/生存/占い/人狼完封の加点、終了後ランキング）
- 匿名Firebase認証を利用した端末間参加と本人用役職情報の分離
- 役職配布、役職確認、夜の行動、公開朝結果、議論、投票、再投票、勝敗判定、再戦
- 管理者の一時停止、再開、時間延長、強制進行、終了、切断者の死亡/保留判断、待機ルーム解散
- 日本語のレスポンシブ画面、役職一覧、遊び方
- 遊び方ページから任意で開始できる操作チュートリアル（入室、役職確認、夜行動、投票、結果確認）。練習内容は端末内だけで動き、Firebaseに接続しません。
- 個人端末で使える推理メモ（役職予想、信頼度、自由記述、記入したフェーズと時刻）。IndexedDBに端末内保存し、Firebaseには送信しません。共有端末では表示せず、次の試合開始時またはルーム退出時に消去します。
- 端末内の試合履歴（直近20試合）。結果、役職、公開設定に従った投票内容、夜行動、公開ログを保存し、管理権限者の端末だけに管理ログも保存します。個別削除・全削除に対応し、端末間同期・エクスポートは行いません。
- GitHub ActionsのPagesビルド/デプロイ

## 外部サービス設定

### Firebase

1. Firebase Consoleでプロジェクトを作成し、Webアプリを登録します。
2. Authenticationで「匿名」プロバイダを有効にします。
3. Realtime Databaseを作成し、リージョンを控えます。Functionsのリージョンは `asia-northeast1` です。
4. Firebase CLIを用意し、`firebase login` と `firebase use --add` でプロジェクトを選択します。
5. Webアプリの設定値を `.env.local` に記入します（`.env.example` を参照）。これらはブラウザー用Firebase識別子であり、秘密鍵ではありません。
6. `firebase deploy --only database,functions` を実行します。Cloud FunctionsのデプロイにはBlazeプランと請求先設定が必要になる場合があります。Functions v2が使えるプロジェクトを使用してください。
7. `database.rules.json` をデプロイします。クライアントに許可する読み取りは `rooms/{code}/signalRevision` の更新番号だけで、ルーム本体の読み取りとすべてのクライアント書き込みは拒否されます。状態の書き換えはFunctions Admin SDKだけが行います。

### ローカル実行

```sh
npm ci
npm run dev
```

Functionsの依存関係を別途導入して型検査する場合は `npm ci --prefix functions && npm run build --prefix functions` を実行してください。Firebase設定前でも画面は開きますが、オンラインルームは利用できません。

### GitHub Pages

1. GitHubにこのプロジェクトをpushし、既定ブランチを `main` にします。
2. Repository Settings → Pages → Build and deployment で「GitHub Actions」を選びます。
3. Settings → Secrets and variables → Actions → Variables に以下を登録します：`VITE_FIREBASE_API_KEY`, `VITE_FIREBASE_AUTH_DOMAIN`, `VITE_FIREBASE_DATABASE_URL`, `VITE_FIREBASE_PROJECT_ID`, `VITE_FIREBASE_APP_ID`。
4. `main`へのpushまたはActionsの手動実行でビルドとPagesデプロイが行われます。Vite設定はリポジトリ名からベースパスを組み立てます。
5. 公開URLを開き、Firebaseの承認済みドメインに `*.github.io` のホスト名を追加し、匿名ログイン、作成、別ブラウザーからの参加を確認します。

## セキュリティ設計と制約

- roomコードは秘密鍵ではありません。Callable APIはFirebase Auth UIDを必須にし、管理操作はルーム内で現在の管理権限を持つUIDだけに許可し、同時に有効な管理者は1人です。
- 通常の呼び出しでは公開/本人/GM情報を分け、DBクライアントルールはread/writeとも拒否します。共有端末モードでは、端末手渡しの待ち時間を減らすため、共有端末の秘密情報も、現在操作している本人の席に対してだけCallable Functionが返します。共有セッションのキャッシュは席が切り替わるたびに前の席の秘密情報を消します。
- 役職配布と勝敗判定、投票集計、襲撃/護衛処理はFunctions側で行います。
- Firebaseプロジェクト自体の作成・課金・ドメイン登録とPages公開操作はリポジトリから代行できません。上の手順が必要です。
- 議論タイマーはサーバー時刻を使い、各操作・heartbeatでも期限を確認します。夜と投票には制限時間を設けず、夜は設定に応じて全員の行動後に自動進行または管理者の手動進行を行います。手動時の完了人数は管理者にだけ返し、一般プレイヤーには待機表示だけを返します。
- 切断通知は管理者に一覧・検知時刻・切断時フェーズを表示し、死亡または保留を選べます。途中フェーズの再開始・巻き戻し、強制退出、未完了者への個別催促は未実装です。管理権限は1人だけが持ち、他の神視点は観戦者として扱います。観戦者は申請し、管理者が承認した間だけ進行中の役職・個別情報を見られます。霊媒結果と占い結果は本人用ビューに分けて返し、ゲームマスターがプレイヤーを兼ねる場合も他人の結果は取得できません。
- ルームはCloud Functionsの定期処理で、開始前の放置ルームは作成から5分後、試合終了後は10分後、試合中に全プレイヤーが切断した場合は切断から10分後に削除します。確認間隔により最大約1分遅れる場合があります。
- FirebaseプロジェクトとCloud Functionsへの接続は確認しましたが、Firebase Emulatorによる統合テスト構成を追加しました（手順と検証範囲は下記）。実端末の画面操作による通し確認、通信量・待ち時間の計測は未実施です。オープンルールと初日白通知を実装済みです。暗殺者ルールは仕様対象から削除しています。

## テストと確認

### 単体テスト

`npm test` は従来の `src` 配下のVitest単体テスト51件を実行します。統合テストは独立したNode.js test runnerで実行し、単体テストにはEmulatorやJavaを要求しません。

### Firebase Emulator統合テスト

前提: Node.js 20、npm、Java 21。初回はnpmレジストリとFirebase Emulatorバイナリのダウンロードへのネットワーク接続が必要です。Firebaseへのログイン、Blaze、本番の環境変数・サービスアカウントは不要です。

```sh
npm ci
npm ci --prefix functions
npm test
npm run test:integration
```

統合コマンドがFunctionsをビルドし、固定バージョンのFirebase CLI（14.12.0）でAuth（9099）、Functions（5001）、Realtime Database（9000）を127.0.0.1上に起動します。テスト成功・失敗後に `emulators:exec` が終了処理を行います。ポートが使用中なら既存プロセスを止めて再実行してください。`listen EPERM` の環境ではローカル実行できないため、同じコマンドを実行するGitHub Actionsを利用してください。

- 専用の `firebase.emulator.json` と固定プロジェクト `demo-jinrou-integration` を使用し、`.firebaserc` の本番選択や `.env.local` を読みません。本番用 `firebase.json` は変更しません。
- テストのURLはすべて127.0.0.1に固定し、Emulator環境変数・プロジェクトIDが一致しなければ通信前に失敗します。起動スクリプトは認証資格情報の環境変数も子プロセスから除去します。
- 本番と同じFunctionsコードと `database.rules.json` を使います。ルームや秘密情報の管理用直接書き込み・Rules無効化はせず、匿名AuthのトークンとCallable HTTPプロトコル、Database REST APIを使います。拒否テストは実際のHTTP権限エラーを検証します。
- 実行ごとに新しい匿名UIDとルームを作成し、ディスクへのデータexport/importを行いません。既存の本番データに接続・変更しません。
- CLI本体のバージョンを固定していますが、CLIの推移的依存はnpm解決に従います。既存のアプリ・Functions依存は変更せず既存lockfileと `npm ci` を使用します。

| 範囲 | 自動検証 |
| --- | --- |
| ルーム | 5桁コード、作成再試行の同一コード、参加、上限超過、解散 |
| 認証・権限 | 未認証拒否、非参加者拒否、GMなりすまし拒否、他人の席指定拒否、管理進捗・開始・解散の権限制限 |
| Database Rules | GM・参加者・観戦者の通知番号読み取り許可、未認証・非参加者の拒否、ルーム本体・役職・行動・票・チャット本文・presence・作成要求の読み取り拒否、PUT/PATCH/DELETE拒否 |
| 3人・20人 | 別UIDで作成・参加・役職確認・初夜完了・朝確認・議論・全員投票・処刑・村勝利・再戦・次試合開始 |
| 秘密情報 | 一般参加者は自分の役職だけ取得、GMのみ役職公開、観戦者は秘密情報なし |
| 同票 | 同票対象の一致、候補者の再投票拒否、対象外投票拒否、残りの投票者による処刑決定 |

3人・20人のシナリオは市民と人狼1人の単純な編成、初日襲撃なしを使用します。役職抽選の結果はGMの正規APIで確認し、人狼へ投票して勝敗を再現します。議論と処刑発表後の進行は管理者の正式な強制進行APIを使用し、夜の完了・全員投票・勝敗判定自体はスキップしません。

`.github/workflows/test.yml` はPR、mainへのpush、手動実行で上記を実行し、失敗時もEmulatorログを7日間保存します。本番FirebaseのSecrets/Variablesは渡さず、既存のPages公開ワークフローとは独立しています。PRのChecksで結果を確認してください。構成追加と実行成功を区別し、CIの成功前に検証済みとして扱わないでください。

このテストは独立した認証ユーザーによるバックエンド統合テストです。別ブラウザー・スマートフォンの画面操作、共有端末の通し操作、全特殊役職の組合せ、回線断・遅延・同時操作負荷、通信量測定は対象外で、引き続き別途確認が必要です。

### 役職構成の保存

作成画面で役職構成に名前を付けて保存できます。保存先は作成端末のブラウザー内です。別の端末やブラウザーには同期されません。読み込む人数に合わせて市民人数だけを調整します。

### 共有端末モード

ルーム作成時に「全員共有」または「併用」を選び、共有端末を使う人の名前を登録します。併用でホストがプレイヤー参加する場合は、ホスト名も共有端末プレイヤー欄に含めます（ホストを別の個人端末プレイヤーとして重複登録しません）。「全員が自分の端末を使用」では、この名前欄は表示されません。画面の案内に従って「○○さんに渡してください」→「○○さんですか？」と確認し、本人が役職や操作を済ませたら次の人へ端末を渡します。共有端末では名前確認だけを行い、PINは使いません。ホスト端末を順番に手渡すカジュアルな遊び方を想定しています。

### ポイント制

ルーム作成時に有効/無効を選べます。有効の場合、ゲーム終了後にホストが「次へ（順位を見る）」を押すと、そのルームの累計順位と今回の加点内訳が公開されます。再戦では累計点を維持し、試合ごとの加点記録だけを初期化します。加点はCloud Functions側で一度だけ処理します。占い成功は人狼を占い当てた場合、人狼ノー投票（完封）は人狼陣営勝利かつ全人狼が投票を一度も受けなかった場合として扱います。

### ホスト権限と神視点の役職公開

ルーム作成時にホストを「プレイヤー（管理権限あり）」または「ゲームマスター」から選べます。プレイヤーを選んでもホストは管理操作を利用できますが、他のプレイヤーの秘密情報は見られません。ゲームマスター表示の有無を設定でき、プレイヤーを兼ねない管理者だけに適用されます。観戦者は役職公開を申請でき、権限者の承認中だけ情報が表示されます。役職確認中は待機画面を返します。

### 特殊ルール

- **オープンルール**：襲撃・処刑で死亡したプレイヤーの役職を結果画面で全員に公開します。発表演出中はサーバー側でも次フェーズへの移行を待機させます。
- **初日白通知**：ゲーム開始時に人狼以外から1人をサーバー側で抽選し、初日の朝、議論直前に「○○さんは白です」と告知します。
- **暗殺者**：選択肢から削除しています。

### 共有者の夜間チャット

共有者は夜フェーズ中、自分以外の生存共有者と専用チャットで会話できます。チャット本文は共有者本人のサーバー応答にだけ含め、他の役職・観戦者には配信しません。全員共有モードでは同じ端末を順番に渡すため、共有者役職は選べません（個人端末・併用モードでは選択できます）。

### Realtime Databaseの通信量と更新遅延

- 通常の画面更新では `rooms/{code}/signalRevision` の小さな番号だけをRealtime Databaseで購読します。投票・再投票・夜フェーズ・役職確認中は、細かな行動ごとの画面取得を止め、`rooms/{code}/progressRevision`（フェーズ移行、一時停止、管理者交代などの進行上重要な変更）だけを購読します。重要な変更があった時にだけCallable Functionから画面情報を取得します。管理者と共有端末セッションは必要な進捗をすぐ確認できる既存の更新経路を保ちます。
- 接続維持のheartbeatは表示中10秒ごと、バックグラウンドでは30秒ごとです。切断の猶予は15秒で、次のheartbeatまたは定期確認で切断状態を反映します。
- heartbeatの時刻は `roomPresence/{code}` に分離して保存します。ルーム本体へのハートビート書き込みが投票・夜行動のRealtime Databaseトランザクションと競合して再試行を起こしていたためです。ルームの参加者だけがCallable Function経由で更新し、クライアントからpresence情報を直接読んだり書いたりするルールはありません。ルーム削除時にpresenceも削除します。
- 通常画面では更新通知を受けて最新状態を取得します。投票中は他人の票を都度取得せず、夜は他人の個別行動を都度取得しません。最終投票・全夜行動の完了などでフェーズが進んだ時に最新画面を1回取得します。夜間チャットは許可された相手だけが専用通知を受け取り、届いた会話は引き続き即時取得します。たとえば投票中に他の7人の票が順に確定しても、個人端末の一般プレイヤーが取得する全体画面は通常、同じ投票フェーズ内の最大7回からフェーズ移行時の1回にまとまります。実際の体感時間や転送バイト数はFirebase実環境で計測していません。
- 夜の「怪しい人投票」は選択時にはサーバーへ送らず、本人の画面に一時保持します。「夜の行動を終える」ときに投票先を夜行動完了と一緒に送るため、この操作では従来の投票確定用Callable呼び出しとRTDB更新を1回省きます。ゲームを確定するサーバー側の検証は完了操作時に行います。夜明けへの移行時も、すでに返ってきた行動応答またはheartbeatの画面情報を使い、同じ状態を取得する追加Callableを行いません。
- 公開画面情報と本人の秘密情報はタブを閉じると消えるsessionStorageに保存し、再読み込み直後の表示に利用します。共有端末では操作中の席の秘密情報だけをsessionStorageに一時保存し、席を切り替えると前の席の秘密情報を消します。sessionStorageのキャッシュは表示を速めるためのもので、操作や勝敗の正しさは引き続きサーバー側で検証します。
