# 月影の村 — オンライン人狼

React + TypeScript + Vite の日本語Webアプリです。GitHub Pagesは静的フロントエンドを配信し、Firebase Authentication（匿名認証）と Callable Cloud Functions がルーム状態・役職・行動・勝敗を管理します。Realtime Databaseのルーム本体はクライアントから読めず、Cloud FunctionsだけがAdmin SDKで読み書きします。認証済みクライアントは更新番号と、共有・人狼チャットの参加者向け更新番号だけを購読できます。参加者に返す画面情報は関数内で整形します。

## 現在の実装範囲

- ルーム作成、5桁コード発行、参加、招待URL/QR、3〜20人の人数チェック
- 人数別おすすめ役職構成、議論時間、夜と役職確認の自動/手動進行、初日襲撃、同票処理、投票結果公開、オープンルール、初日白通知
- ポイント制（ルーム内累計、勝利/生存/占い/人狼完封の加点、終了後ランキング）
- 匿名Firebase認証を利用した端末間参加と本人用役職情報の分離
- 役職配布、役職確認、夜の行動、公開朝結果、議論、投票、再投票、勝敗判定、再戦
- 管理者の一時停止、再開、時間延長、強制進行、終了、切断者の死亡/保留判断、待機ルーム解散
- 日本語のレスポンシブ画面、役職一覧、遊び方
- GitHub ActionsのPagesビルド/デプロイ

## 外部サービス設定

### Firebase

1. Firebase Consoleでプロジェクトを作成し、Webアプリを登録します。
2. Authenticationで「匿名」プロバイダを有効にします。
3. Realtime Databaseを作成し、リージョンを控えます。Functionsのリージョンは `asia-northeast1` です。
4. Firebase CLIを用意し、`firebase login` と `firebase use --add` でプロジェクトを選択します。
5. Webアプリの設定値を `.env.local` に記入します（`.env.example` を参照）。これらはブラウザー用Firebase識別子であり、秘密鍵ではありません。
6. `firebase deploy --only database,functions` を実行します。Cloud FunctionsのデプロイにはBlazeプランと請求先設定が必要になる場合があります。Functions v2が使えるプロジェクトを使用してください。
7. `database.rules.json` をデプロイします。クライアントに許可する読み取りは `rooms/{code}/signalRevision` の更新番号だけで、ルーム本体の読み取りとすべてのクライアント書き込みは拒否されます。状態の書き換えはFunctions Admin SDKだけが行います。

### ローカル実行

```sh
npm ci
npm run dev
```

Functionsの依存関係を別途導入して型検査する場合は `npm ci --prefix functions && npm run build --prefix functions` を実行してください。Firebase設定前でも画面は開きますが、オンラインルームは利用できません。

### GitHub Pages

1. GitHubにこのプロジェクトをpushし、既定ブランチを `main` にします。
2. Repository Settings → Pages → Build and deployment で「GitHub Actions」を選びます。
3. Settings → Secrets and variables → Actions → Variables に以下を登録します：`VITE_FIREBASE_API_KEY`, `VITE_FIREBASE_AUTH_DOMAIN`, `VITE_FIREBASE_DATABASE_URL`, `VITE_FIREBASE_PROJECT_ID`, `VITE_FIREBASE_APP_ID`。
4. `main`へのpushまたはActionsの手動実行でビルドとPagesデプロイが行われます。Vite設定はリポジトリ名からベースパスを組み立てます。
5. 公開URLを開き、Firebaseの承認済みドメインに `*.github.io` のホスト名を追加し、匿名ログイン、作成、別ブラウザーからの参加を確認します。

## セキュリティ設計と制約

- roomコードは秘密鍵ではありません。Callable APIはFirebase Auth UIDを必須にし、管理操作はルーム内で現在の管理権限を持つUIDだけに許可し、同時に有効な管理者は1人です。
- 通常の呼び出しでは公開/本人/GM情報を分け、DBクライアントルールはread/writeとも拒否します。共有端末モードでは、端末手渡しの待ち時間を減らすため、共有端末の秘密情報も、現在操作している本人の席に対してだけCallable Functionが返します。共有セッションのキャッシュは席が切り替わるたびに前の席の秘密情報を消します。
- 役職配布と勝敗判定、投票集計、襲撃/護衛処理はFunctions側で行います。
- Firebaseプロジェクト自体の作成・課金・ドメイン登録とPages公開操作はリポジトリから代行できません。上の手順が必要です。
- 議論タイマーはサーバー時刻を使い、各操作・heartbeatでも期限を確認します。夜と投票には制限時間を設けず、夜は設定に応じて全員の行動後に自動進行または管理者の手動進行を行います。手動時の完了人数は管理者にだけ返し、一般プレイヤーには待機表示だけを返します。
- 霊媒結果の安全な個別受け渡し、切断通知の保留一覧/時刻/フェーズ表示、途中フェーズの再開始・巻き戻し、強制退出、未完了者への催促は未完成です。管理権限は1人だけが持ち、他の神視点は観戦者として扱います。観戦者は申請し、管理者が承認した間だけ進行中の役職・個別情報を見られます。
- ルームはCloud Functionsの定期処理で、開始前の放置ルームは作成から5分後、試合終了後は10分後、試合中に全プレイヤーが切断した場合は切断から10分後に削除します。確認間隔により最大約1分遅れる場合があります。
- Firebase未接続のため、複数端末統合・権限境界の実環境確認は未実施です。オープンルールと初日白通知を実装済みです。暗殺者ルールは仕様対象から削除しています。

## テストと確認

`npm test` はVitestを起動します。Firebase Emulatorを使う統合テスト環境は未構成です。Firebase接続後は、別ブラウザー/端末、一般参加者とGM、Database Rules拒否、3人/20人、投票・同票・再戦の確認が必要です。未実施の項目を実施済みとして扱わないでください。
### 役職構成の保存

作成画面で役職構成に名前を付けて保存できます。保存先は作成端末のブラウザー内です。別の端末やブラウザーには同期されません。読み込む人数に合わせて市民人数だけを調整します。

### 共有端末モード

ルーム作成時に「全員共有」または「併用」を選び、共有端末を使う人の名前を登録します。併用でホストがプレイヤー参加する場合は、ホスト名も共有端末プレイヤー欄に含めます（ホストを別の個人端末プレイヤーとして重複登録しません）。「全員が自分の端末を使用」では、この名前欄は表示されません。画面の案内に従って「○○さんに渡してください」→「○○さんですか？」と確認し、本人が役職や操作を済ませたら次の人へ端末を渡します。共有端末では名前確認だけを行い、PINは使いません。ホスト端末を順番に手渡すカジュアルな遊び方を想定しています。

### ポイント制

ルーム作成時に有効/無効を選べます。有効の場合、ゲーム終了後にホストが「次へ（順位を見る）」を押すと、そのルームの累計順位と今回の加点内訳が公開されます。再戦では累計点を維持し、試合ごとの加点記録だけを初期化します。加点はCloud Functions側で一度だけ処理します。占い成功は人狼を占い当てた場合、人狼ノー投票（完封）は人狼陣営勝利かつ全人狼が投票を一度も受けなかった場合として扱います。

### ホスト権限と神視点の役職公開

ルーム作成時にホストを「プレイヤー（管理権限あり）」または「ゲームマスター」から選べます。プレイヤーを選んでもホストは管理操作を利用できますが、他のプレイヤーの秘密情報は見られません。ゲームマスター表示の有無を設定でき、プレイヤーを兼ねない管理者だけに適用されます。観戦者は役職公開を申請でき、権限者の承認中だけ情報が表示されます。役職確認中は待機画面を返します。

### 特殊ルール

- **オープンルール**：襲撃・処刑で死亡したプレイヤーの役職を結果画面で全員に公開します。発表演出中はサーバー側でも次フェーズへの移行を待機させます。
- **初日白通知**：ゲーム開始時に人狼以外から1人をサーバー側で抽選し、初日の朝、議論直前に「○○さんは白です」と告知します。
- **暗殺者**：選択肢から削除しています。

### 共有者の夜間チャット

共有者は夜フェーズ中、自分以外の生存共有者と専用チャットで会話できます。チャット本文は共有者本人のサーバー応答にだけ含め、他の役職・観戦者には配信しません。全員共有モードでは同じ端末を順番に渡すため、共有者役職は選べません（個人端末・併用モードでは選択できます）。

### Realtime Databaseの通信量と更新遅延

- 画面更新はルーム全体のポーリングではなく、`rooms/{code}/signalRevision` の小さな番号をRealtime Databaseで購読します。Functionsがルーム状態を更新すると同じトランザクション内で番号が進み、クライアントは通知を受けた時だけCallable Functionから自分の権限に応じた画面情報を取得します。
- 更新通知には役職・投票先・夜の行動・ログなどを含めません。ルーム本体は従来どおりクライアントから読めず、画面情報の権限確認はFunctionsが行います。更新番号の購読が失敗した場合は、heartbeatの画面情報取得へ自動的に戻ります。
- 接続維持のheartbeatは議論中は表示中5秒ごと、他のフェーズは15秒ごと、バックグラウンドでは30秒ごとです。切断の猶予は15秒で、次のheartbeatまたは定期確認で切断状態を反映します。
- 他端末の変更反映は、次の定期確認を待たず更新通知を受けてから画面情報を取得します。実際の体感時間はネットワークやFunctionsの応答時間に左右されます。転送量は計測していないため、具体的なバイト削減量は未確認です。
- 公開画面情報と本人の秘密情報はタブを閉じると消えるsessionStorageに保存し、再読み込み直後の表示に利用します。共有端末では操作中の席の秘密情報だけをsessionStorageに一時保存し、席を切り替えると前の席の秘密情報を消します。sessionStorageのキャッシュは表示を速めるためのもので、操作や勝敗の正しさは引き続きサーバー側で検証します。
